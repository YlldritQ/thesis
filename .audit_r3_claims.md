# R3 clean-room claims, notebooks, dashboard, and cross-artifact audit

Scope: current repository source, Parquet/JSON/JSONL artifacts, notebooks, and
Streamlit pages. No remediation was performed before recording this note.

Independence disclosure: the direct checks below were designed and run before
the R2/R2.1 reconciliation. A broad repository grep intended to exclude the two
review files unexpectedly emitted some snippets from them before this note was
written. None of the findings below relies on those snippets: each is supported
by a direct command, current source line, current artifact, or primary OCDS
documentation. The three parallel Phase-1 reviewers remained explicitly
isolated from R2/R2.1 and provide independent corroboration.

## Independent findings

### C-01 — P1 — Award-stage data is repeatedly presented as signed-contract data

- Current raw objects have a non-standard `award` array but no `contracts`
  section. Direct scan: 75,710 compiled objects, 65,721 raw `award` objects,
  and zero top-level `contracts` objects. The OCP Publication 115 registry also
  reports that `awards` is misspelled as `award`, and reports zero standard OCDS
  contracts. OCDS formally separates award decisions from signed contracts.
- `src/thesis/narrative.py:29-37,95-97,344-346` describes award totals and award
  counts as amounts/contracts “contracted”; `streamlit_app/Home.py:87`,
  `streamlit_app/pages/1_Overview.py:62-68`,
  `streamlit_app/pages/2_Explore.py:143-148`, and
  `streamlit_app/pages/3_Anomalies.py:388` repeat that claim.
- Impact: the €4.7655bn total and 54,133-tender count are valid as sums/counts of
  *reported award records after deduplication*, not evidence of signed contract
  values or executed spending. Contract amendments and implementation are not
  observable. This changes interpretation, not the numeric sum.
- Required remediation: retain historical internal column names for compatibility
  but relabel every user-facing statement as “reported award value/decision”; add
  an explicit no-signed-contract/no-implementation limitation and primary OCDS
  citation; rename notebook prose that calls tender records “contracts.”

### C-02 — P1 — Manual-audit metadata falsely claims 100% usable source URLs

- `data/review/manual_audit_sample.csv` has 150 rows and 150 nonblank URL strings,
  but 31 are the malformed publisher placeholder
  `.../DokumentPodaciFrm.aspx?id=`. Thus only 119/150 (79.33%) have a usable exact
  document URL; all 31 malformed sample records have no valid alternate document
  URL in their raw object.
- Population scan: all 75,710 raw records have a nonblank document string, but
  only 58,368 have a structurally usable URL; 17,342 (22.91%) contain only a
  blank-ID placeholder.
- `src/thesis/audit.py:65-76` accepts any nonblank string and
  `data/review/manual_audit_sample.metadata.json` therefore reports
  `source_document_url_coverage_pct: 100.0`.
- Impact: the queue overstates document retrievability and can send reviewers to
  a non-document URL.
- Required remediation: validate scheme/host and reject blank required query
  identifiers; leave unavailable URLs blank, add an availability/reason field,
  regenerate metadata honestly, and test the 119/150 result.

### C-03 — P1 — Audit regeneration can destroy completed human work

- `src/thesis/audit.py:190-215` refuses overwrite by default but `force=True`
  replaces the entire CSV and unconditionally recreates every review field as
  blank (`src/thesis/audit.py:161-163`). The CLI advertises this force path.
- Current queue has zero completed labels, so no human work has yet been lost.
- Impact: a future normal regeneration command can erase irreplaceable evidence,
  contrary to the documented preservation promise.
- Required remediation: even under force, detect nonblank human fields and either
  preserve them by stable `ocid`/`audit_id` merge or refuse; add destructive-path
  regression tests. Regenerating the current unlabeled queue is safe.

### C-04 — P2 — The documented type-check gate is failing

- Baseline command: `.venv/bin/python -m mypy src/thesis` exits 1 with 13 errors
  in `narrative.py`, `domain/schemas.py`, `logging.py`, `anomaly/models.py`,
  `anomaly/benchmark.py`, and `pipeline/ml.py`.
- In the same clean baseline, Ruff lint and format passed, all DQ suites passed
  (one nonblocking silver-tender warning), DAG status showed all stages fresh,
  and pytest reported 194 passed.
- Impact: README/Makefile imply a working quality gate that the repository does
  not satisfy; some errors obscure real optional/Any assumptions.
- Required remediation: correct annotations/narrowing rather than disabling the
  checks; rerun mypy and the full suite.

### C-05 — P2 — JSON writer can emit wrong types and non-standard numbers

- `src/thesis/io/writers.py:74-80` uses
  `json.dumps(..., default=str)` with the default `allow_nan=True`.
- Consequences: `numpy.bool_(True)` serializes as the JSON string `"True"`, NumPy
  numbers/dates are stringified, and NaN/Infinity can be emitted as invalid
  strict-JSON tokens. Current canonical releases happen not to contain the
  searched bad tokens, but the shared writer has no contract preventing them.
- Impact: future DQ/release metadata can change type silently and fail downstream
  validation or cross-language use.
- Required remediation: explicit conversion for NumPy scalar/bool and datetime/
  date/Path, map missing numeric values to JSON null or reject them by contract,
  set `allow_nan=False`, and add round-trip tests.

### C-06 — P2 — Silver readers are not generation-bound and permit mixed UI data

- `src/thesis/io/readers.py:27-34` reads silver Parquet directly with no release
  manifest. The silver DAG task has only timestamp freshness and no manifest
  (`src/thesis/pipeline/dag.py:89-95`).
- Gold/ML readers validate their own release hashes, but Explore and Entities load
  current silver awards separately next to released gold. Changing
  `data/silver/awards.parquet` can therefore mix a different silver generation
  with still-valid gold/model data in one page. Validating ML's hash of the
  `gold.release.json` bytes is not recursive validation of gold's silver inputs.
- Impact: tender detail/supplier rows shown beside scores can come from different
  generations; silver freshness depends only on mtime.
- Required remediation: publish a Silver release manifest last, bind both silver
  Parquets and DQ checks, make readers validate it, include the manifest as the
  gold input, and validate prerequisite releases in DAG/reader paths.

### C-07 — P2 — Code provenance is unavailable although lineage implies it

- The project root is not a Git repository. Current lineage sidecars consequently
  record `git_sha: "unknown"` (for example
  `data/gold/tender_summary.parquet.lineage.json`) while README says each sidecar
  records a git SHA.
- Releases bind data/artifact bytes and protocol metadata well, but they do not
  bind the source tree when Git metadata is absent.
- Impact: exact code provenance cannot be reconstructed from shipped artifacts.
- Required remediation: add a deterministic source-tree fingerprint to lineage
  and stage release metadata, and document Git SHA as optional/unavailable in
  this export. This is not recoverable as a historical commit without external
  evidence.

### C-08 — P2 / human-method choice — Rule threshold is highly discontinuous

- Exact recomputation from current gold matches all 13 rule columns and
  `rule_score` byte-for-value. Only four rules score; the score distribution is:
  0.0=48,322; 0.125=18,420; 0.25=255; 0.375=8,492; 0.5=24;
  0.625=120; 0.75=68; 1.0=9.
- Counts above alternate thresholds are 27,388 at 0.1; 8,968 at 0.2; 8,713 at
  0.3; 221 at 0.4/0.5; 197 at 0.6; 77 at 0.7; 9 at 0.8. The 0.5 operating
  threshold is therefore an author choice, not a stable empirical boundary.
- `HIGH_VALUE_SINGLE` necessarily overlaps one of the two mutually exclusive
  single-bidder signals (101/101 cases), so priority partly reflects intentional
  interaction/stacking rather than independent evidence.
- Impact: reporting one flagged count without nearby sensitivity can imply more
  stability than exists.
- Required remediation: add threshold and top-rank-quantile sensitivity to the
  generated findings/validation artifacts, explicitly as sensitivity rather
  than validation. Choosing new weights or an operating point requires human/
  external evidence and must not be invented during remediation.

### C-09 — P3 — Notebook evidence posture is mostly safe but inconsistent

- Both notebooks parse as nbformat 4; every code cell passes Python AST parsing;
  both have zero outputs and zero execution counts.
- `02_data_quality.ipynb` starts with an explicit outputs-cleared/current-evidence
  banner. `01_eda.ipynb` only gives the warning near its final cell and retains
  “Fill in after running” placeholders.
- Impact: no stale numeric output is currently presented, but the EDA notebook's
  opening can be clearer and its “contracts” terminology is semantically wrong.
- Required remediation: add the same top banner, replace contract terminology
  with tender/process terminology, and retain placeholders as explicitly
  non-evidence or remove them.

### C-10 — P2 — The shipped Docker health check calls a missing executable

- `Dockerfile:13-16` installs `curl` only in the discarded builder stage.
  The runtime stage (`Dockerfile:25-43`) does not install it, while
  `Dockerfile:63-64` defines the health check as `curl -f ...`.
- Impact: a successfully started dashboard container can be marked unhealthy
  solely because the health-check command is absent; Compose restart/health
  behavior is therefore unreliable.
- Required remediation: use Python's standard-library HTTP client in the
  health check (already present in runtime) or explicitly install curl; verify
  with a Docker build when a Docker daemon is available.
